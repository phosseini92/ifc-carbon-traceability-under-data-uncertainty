# Methods and limitations — v0.2

## 1. Research design

The demonstrator studies data reliability in a deliberately bounded IFC-to-carbon
screening chain. It separates three forms of validity:

1. **Structural integrity:** required quantities, units, GUIDs, geometry and material
   fields are present and internally consistent.
2. **Mapping integrity:** the active material-to-database mapping matches a recorded
   review contract containing the intended source record ID and UUID.
3. **Semantic validity:** the selected environmental record is actually appropriate for
   the product, geography, technology, boundary and intended comparison.

The first two are partially automatable in this project. The third is not established by
software consistency and remains an explicit human/expert-review requirement.

## 2. Accounting

For each accepted monolithic element *i* mapped to source record *m*:

`mass_i = NetVolume_i [m3] × density_m [kg/m3]`

`GHG_i = mass_i [kg] × fabrication_factor_m [kg CO2e/kg]`

The screening total covers selected materials in four walls and one slab only. It is not
normalised to a building functional unit and does not establish functional equivalence
between alternative materials.

KBOB/ecobau 2022 v9.0 row 38 (01.002) supplies generic unreinforced concrete:
2300 kg/m3 and 0.0887 kg CO2e/kg. Row 83 (02.001) supplies generic fired brick:
900 kg/m3 and 0.254 kg CO2e/kg. Column AA is the published Fabrication value used
here. Row 88 (02.003), 700 kg/m3 and 0.167 kg CO2e/kg, is retained only as a controlled
wrong-record mapping. These densities are generic source proxies, not site measurements.

The project does **not** assert that KBOB Fabrication is identical to EN 15804 A1-A3.

## 3. Geometry and quantity checks

The controlled fixture uses closed extruded solids stored in IFC4 and parsed with
IfcOpenShell. Geometry-engine volume is calculated independently from the declared
`NetVolume` quantity. Project length and volume units are interpreted explicitly.

A quantity passes when:

`abs(declared_volume - geometry_volume) / geometry_volume <= 0.01`

The 1% threshold is an author-declared QA tolerance, not an IFC standard requirement.
The metre/mm fixtures test unit interpretation; a hand calculation provides an
independent arithmetic benchmark.

Comparing geometry and quantity representations generated by the same authoring code is
still an internal consistency test. That is why v0.2 adds a third-party IFC fixture for
import/material/geometry inspection, without claiming it validates the carbon workflow.

## 4. Material assignment and mapping contract

The carbon-release workflow supports one direct/inherited `IfcMaterial` per `IfcWall` or
`IfcSlab`. Layered or multi-material assignments are rejected because defensible carbon
allocation requires explicit layer quantities.

A separate descriptor can inspect `IfcMaterialLayerSetUsage` and `IfcMaterialLayerSet`
so independently authored files can be characterised without silently forcing them into
the monolithic accounting model.

The active material mapping is stored in `inputs/material_mapping.json`. A second file,
`inputs/material_mapping_contract.json`, records the intended KBOB record ID, UUID,
review status and review basis. A mismatch blocks release. This protects against
configuration drift or accidental remapping.

**Important limitation:** the contract is not proof of semantic correctness. The
`plausible_wrong_mapping_approved` experiment intentionally changes both the mapping and
its contract to a valid but unsuitable record. Automated checks can then remain
internally consistent while the environmental result is wrong. This is the central
semantic blind spot of the demonstrator.

## 5. Controlled fault injection

The main fixture defines seven cases:

| Case | Failure mechanism | Expected behaviour |
|---|---|---|
| complete | clean controlled baseline | release screening total |
| missing_material | one wall loses material assignment | block |
| unmapped_material | material name has no source mapping | block |
| volume_x1000 | declared wall volume multiplied by 1000 | block |
| duplicate_guid | two walls share a GUID | block |
| mapping_tamper | mapping changes but review contract does not | block |
| plausible_wrong_mapping_approved | valid wrong record and matching wrong contract | passes automated checks; semantic blind spot |

This is a deliberately small fault set. No detection rate may be generalised to arbitrary
IFC models.

## 6. Uncertainty

Accepted deterministic values are perturbed with independent triangular multipliers:

| Variable | Lower | Mode | Upper | Shared across |
|---|---:|---:|---:|---|
| Quantity | 0.98 | 1 | 1.02 | each element independently |
| Density | 0.95 | 1 | 1.05 | all elements using the same record |
| Fabrication factor | 0.80 | 1 | 1.20 | all elements using the same record |

These are illustrative epistemic assumptions defined by the author. They are not KBOB
uncertainty estimates, measured variation or empirical confidence bounds. Missing data
are not imputed probabilistically.

Stable SHA-256 keyed NumPy streams make results insensitive to element ordering and
allow smaller samples to be exact prefixes of larger runs. Convergence is examined at
1,000, 2,500, 5,000, 10,000 and 25,000 draws across three seeds.

Version 0.2 also screens quantity, density and factor uncertainty families separately.
The resulting P05–P95 widths are descriptive sensitivity evidence, **not** a formal
variance decomposition.

`one_at_a_time_sensitivity.csv` (present since v0.1 but undocumented until this v1.0
audit) is a separate, deterministic complement to the Monte Carlo analysis above. For
each source record and for `density` and `factor` only (not quantity), it recomputes
the nominal total with that one variable held at its configured low or high triangular
endpoint and every other variable held at its nominal value, using
`total = nominal + record_contribution × (multiplier − 1)`. This is exact under the
model's own linear multiplicative structure (`GHG = Σ volume × density × factor`), but
it is a one-variable-at-a-time deterministic perturbation, not a probabilistic draw, and
it does not cover quantity uncertainty. It should be read alongside, not instead of, the
Monte Carlo and family-screening results above.

## 7. External IFC interoperability probe

`inputs/external/IfcScript_Slab.ifc` is an independently authored IFC4 example from the
public buildingSMART-community IfcScript repository and reports GeometryGymIFC as the
preprocessor. It uses `IfcMaterialLayerSetUsage`, a different material convention from
the controlled fixture.

`check_external_ifc.py` is intended to record schema, authoring-system metadata,
geometry volume and material-layer structure. It does not release a carbon total because
the fixture does not meet the strict monolithic quantity/allocation contract. One
external sample is a probe, not general IFC validation.

## 8. Provenance and reproducibility

The KBOB source landing page, workbook URL/version, selected row/column values, UUIDs
and source hash are recorded under `inputs/`. The full source workbook is not
redistributed.

Fresh runs create a manifest containing Python/package versions, seed, draw count,
input-model hash, source/input hashes and output hashes. The manifest excludes its own
hash to avoid recursion.

The mapping contract is itself hashed as an input. This allows a future reviewer to tell
whether a numerical result was produced under the same mapping assumptions and review
record.

## 9. Boundaries

Excluded from the current study:

- roof, openings, mortar, reinforcement, finishes and services;
- construction losses and transport;
- operation, maintenance, replacement and end-of-life;
- full LCA and functional-unit comparison;
- BEM, calibrated building physics and sensor/occupant validation;
- material reuse/circularity credits;
- LC3 or earth-construction case studies;
- empirical or source-derived uncertainty distributions;
- universal IFC import support.
